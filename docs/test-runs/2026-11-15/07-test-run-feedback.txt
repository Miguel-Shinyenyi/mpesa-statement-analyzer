TELEMETRY FAULT, TRACED (2026-11-15)
Cause, confirmed: Claude Code 2.1.322 sends the metric claude_code.token.usage with each count under the key asDouble (a whole number). umwayi/telemetry.py, in fold_metrics, requires the key asInt for every metric except cost.usage, and raises "a count was not an integer from 0 to 10^12" when asInt is missing (line 200). So the receiver refuses the metrics report, marks the run invalid, stops it with exit 2, and settles the full reservation.
How I traced it:
- I wrote a small local receiver in my scratchpad (shape_recv.py, not in the pack). It logs only key names and value types, never values or content.
- I ran claude -p once with the same OTEL settings umwayi sets (the code is telemetry_env in umwayi/telemetry.py), pointed at that receiver.
- The metrics report: claude_code.cost.usage has asDouble (a float). claude_code.token.usage has asDouble too, with a whole number. umwayi accepts asDouble only for cost.
- The log report (the api_request event) sends cost_usd_micros and the four token counts as intValue. umwayi accepts those. That is why the settle line showed tokens (input 2, output 4, cache read 9012, cache creation 10109) and still said 1 report refused.
Why the fakes passed: the tests send asInt. A real Claude Code 2.1.322 does not. I did not check older versions.
What I did not do: I did not change umwayi-os. A fix would accept asDouble for the token metric when the number is a whole number from 0 to 10^12, as it already does for cost. That is a design choice for you (it loosens an input check on the budget path), so I left it.
An aside: a shell with ANTHROPIC_API_KEY set made my direct run fail with "Invalid API key". umwayi strips credential variables itself, so its own run was not affected.

CHECKLIST ITEMS FOR UMWAYI-OS (from this run, 2026-11-15)
Item 1: Claude Code cost report is refused, so a good run ends as a failure.
- Where: umwayi/telemetry.py, Totals.fold_metrics, the line that raises "a count was not an integer from 0 to 10^12" when "asInt" is not in the data point (line 200 on main 7da3e67).
- What happens: Claude Code 2.1.322 sends claude_code.token.usage counts as "asDouble" with a whole number. umwayi accepts asDouble only for claude_code.cost.usage. So the run is marked invalid, stops with exit 2, and the full reservation is settled as "unknown".
- Proof: the logbook settle line of the real run (tokens input 2, output 4, cache read 9012, cache creation 10109, "reports accepted 1, refused 1") and the shape capture. Both are in this file. The video umwayi-agent-claude.mp4 shows it.
- Proposed fix, for the owner to decide: in the token branch, accept "asDouble" when the value is a whole number from 0 to 10^12 (for example a float with no fraction), and keep refusing a fraction, a negative number, text, a bool and anything over 10^12. Keep "asInt" accepted as before.
- Why it needs a decision: it loosens one input check on the budget path. The rule "anything else marks the run invalid" is a deliberate safety stance, so the owner should agree to the new rule before it is built.
- Tests to add: a token data point with asDouble 9012.0 is counted as 9012. asDouble 1.5, -1, "9012", true and 1e13 are each refused and mark the run invalid. A data point with neither key is still refused. The existing asInt tests stay.
- A real check to add after the fix: run umwayi agent run on a real Claude Code once and expect exit 0 and a settled "measured" cost, not "unknown". Check the 2.1.322 version in the note, and try one older version if you have it.
- Not known: whether older Claude Code versions send asInt. The fakes in the tests do.
- Owner decision needed: yes (the loosened check).

Item 2 (smaller): the hook file path for Kiro must be the resolved path.
- On macOS a temp folder under /var is really /private/var. umwayi compares the hook command with the resolved root path, so a hand written hook file with /var/... fails the check with a long message. The message could name the resolved path it expected, or the setup docs could say "use the resolved path (pwd -P)". Docs only, no owner decision needed.

Item 3 (smaller): the Homebrew Python path and the fixed test dates, from the test run above.
- The @ in a path like /opt/homebrew/opt/python@3.13/bin/python3.13 is refused by schedule validate. The scenario test test_01 fails and skips 25 steps.
- Some tests use the fixed date 2026-11-13 while the logbook uses the real date, so they fail after midnight.
- Owner decision needed for the first (it is a rule about unit file paths). The second is a test fix.
